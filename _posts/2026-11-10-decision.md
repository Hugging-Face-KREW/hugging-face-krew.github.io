# Hugging Face의 의사결정 모델

대규모 언어 모델(LLM)은 텍스트 생성에 탁월합니다. 우리는 질문에 답하고, 코드를 작성하고, 문제를 추론하는 등 다양한 작업에 이를 사용합니다. *하지만 모든 문제에 텍스트 생성이 필요한 것은 아닙니다.*

다음과 같은 메시지를 받는 고객 지원 시스템을 생각해 보겠습니다.

"구독 요금이 두 번 청구되었습니다. 오늘 환불받고 싶습니다."

시스템은 어떤 팀이 요청을 처리해야 하는지, 얼마나 긴급한지, 고객이 환불을 요청하는지를 판단해야 합니다.

LLM에 이러한 답변을 포함하는 JSON 객체를 반환하도록 요청할 수도 있습니다.

```bash
llama cli -hf ggml-org/gemma-4-e4b-it-GGUF:Q4_0

> We have the following customer support ticket, "I was charged twice for my subscription. I need a refund today.", which team should handle the request, how urgent it is, and whether the customer is requesting a refund. Give the answers in JSON.

[Start thinking]
...
[end thinking]
```json
{
  "team_to_handle": "Billing",
  "urgency": "High",
  "request_refund": true
}
```


하지만 모델이 텍스트를 전혀 생성하지 않고 사용 가능한 선택지를 직접 평가하여 그에 대한 확률 분포를 반환할 수 있다면 어떨까요?

```python
from transformers import pipeline

decide = pipeline("decision", model="autotrust/GEV-26B-Decide")
decision = decide(
    {
        "state": "I was charged twice for my order and want a refund.",
        "questions": {
            "department": {
                "type": "choice",
                "instructions": "Which team should handle this?",
                "criteria": {
                    "billing": "Payments and refunds",
                    "technical": "Bugs and technical issues",
                    "sales": "Pricing and subscriptions"
                }
            },
        }
    }
)

# {
#   'department': {
#       'type': 'choice',
#       'choice': 'billing',
#       'confidence': 0.9974000453948975,
#       'probabilities': {
#         'billing': 0.9982666969299316,
#         'technical': 0.0010246571619063616,
#         'sales': 0.0007087149424478412
#       }
#     }
# }

```


이것이 바로 **의사결정 모델**의 핵심 아이디어입니다.

## 의사결정 모델이란 무엇인가요? {#section-1}

의사결정 모델은 입력 컨텍스트(상태)를 받아, 미리 정의된 가능한 답변 집합(primitive)을 사용해 질문을 평가하고, 확률과 함께 구조화된 결정을 반환합니다. 모델에 토큰 단위로 답변을 생성하도록 요청하는 대신, 애플리케이션이 이미 이해할 수 있는 답변에 확률을 할당하도록 요청하는 것입니다.

![state and primitives for the decision models](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/decision/decision-models.png)

[TypeSafe AI는 Jev를 소개하며](https://typesafe.ai/blog/introducing-system-one-models-and-jev), 이를 [*System One 모델*](https://en.wikipedia.org/wiki/Thinking,_Fast_and_Slow)이라고 설명했습니다. 이 이름은 빠르고 직관적인 사고(System 1)와 더 느리고 숙고하는 사고(System 2)의 구분에서 영감을 얻었습니다.

> 인지 이론을 특정해서 언급하기보다 모델의 계산상 역할을 설명하기 때문에, 커뮤니티에서는 **의사결정 모델**이라는 용어로 의견이 모였습니다. 이 글의 나머지 부분에서는 모델을 "system one 모델" 대신 "의사결정 모델"이라고 부르겠습니다. ([이러한 모델을 어떻게 부를지 결정하기 위해 실시한 twitter 설문](https://x.com/ariG23498/status/2113220513158009022))

의사결정 모델의 기본 인터페이스는 다음과 같습니다.

```text
State + Questions + Allowed Answers → Decisions + Probabilities
```


## 모든 작업에 LLM을 사용하지 않는 이유는 무엇인가요? {#section-2}

LLM에 우리의 결정을 포함하는 JSON 객체를 반환하도록 간단히 프롬프트할 수 있습니다. 실제로 많은 애플리케이션이 이미 분류, 라우팅 및 기타 구조화된 작업에 언어 모델을 이런 방식으로 사용하고 있습니다.

하지만 이 접근 방식에는 몇 가지 문제가 있습니다.

* LLM이 요청된 스키마를 따른다는 보장이 없습니다: 명시적인 지시를 따르더라도 모델은 잘못된 JSON을 생성하거나, 예상치 못한 키를 추가하거나, 허용된 선택지에 없는 답변을 반환할 수 있습니다.
* 제약 디코딩은 도움이 되지만 계산 오버헤드를 없애지는 못합니다: [Outlines](https://github.com/dottxt-ai/outlines) 및 [XGrammar](https://github.com/mlc-ai/xgrammar)와 같은 라이브러리는 각 단계에서 모델이 생성할 수 있는 토큰을 제한하여 문법 또는 JSON 스키마를 강제할 수 있습니다. 이를 통해 출력이 지원되는 구조적 제약을 따르도록 보장할 수 있지만, 추가 작업이 발생합니다.
* 전체 응답을 생성해야 하는 이유는 무엇인가요?: LLM은 개방형 생성을 위해 설계되었지만, 애플리케이션이 미리 정의된 답변 중 하나를 선택하기만 하면 되는 경우에는 자기회귀 디코딩이 불필요한 작업일 수 있습니다.

## 의사결정 모델은 분류 모델과 어떻게 다른가요? {#section-3}

의사결정 모델의 인터페이스를 이해하기 전에, 서로 밀접하게 관련된 두 가지 접근 방식인 전통적 분류와 zero-shot 분류를 다시 살펴보는 것이 유용합니다.

### 전통적 분류

고객 지원 요청을 다음 세 부서로 라우팅하는 분류기를 학습한다고 가정해 보겠습니다.

* 결제
* 기술 지원
* 영업

기존의 분류 모델은 입력을 미리 정의된 레이블 집합에 매핑하는 방법을 학습합니다. 학습 중에 모델은 예시를 통해 이러한 레이블을 예측하는 법을 배웁니다. 일반적으로 분류 헤드는 클래스마다 하나의 로짓을 생성하고, softmax는 이러한 로짓을 확률 분포로 변환합니다.

여기서의 한계는 ***출력 클래스가 모델의 분류 헤드에 내장되어 있다는 것***입니다.

Legal과 같은 네 번째 부서를 추가하더라도 기존 분류기가 이에 대응하는 출력 클래스를 자동으로 얻지는 못합니다. 헤드를 수정하고, 학습 데이터를 수집한 다음, 모델을 **재학습**하거나 조정해야 할 수 있습니다.

### Zero-shot 분류

[Zero-shot 분류](https://huggingface.co/tasks/zero-shot-classification)는 이러한 한계의 중요한 부분을 해결합니다. 분류기가 모든 출력 카테고리에 대해 구체적으로 학습되어 있어야 하는 대신, 추론 시점에 후보 레이블을 제공합니다.

예를 들어:

```python
from transformers import pipeline

classifier = pipeline(
    "zero-shot-classification",
    model="facebook/bart-large-mnli",
)

classifier(
    "My payment was deducted twice.",
    candidate_labels=["billing", "technical support", "sales"],
)

# {'sequence': 'My payment was deducted twice.',
#  'labels': ['billing', 'sales', 'technical support'],
#  'scores': [0.8466812372207642, 0.0962134450674057, 0.05710534751415253]}
```


기존의 고정 레이블 분류기와 달리 카테고리는 요청마다 달라질 수 있습니다. Legal과 같은 다른 부서를 추가하고 모델 출력을 확인해 보겠습니다.

```python
from transformers import pipeline

classifier = pipeline(
    "zero-shot-classification",
    model="facebook/bart-large-mnli",
)

classifier(
    "My payment was deducted twice.",
    candidate_labels=["billing", "technical support", "sales", "legal"],
)

# {'sequence': 'My payment was deducted twice.',
#  'labels': ['billing', 'sales', 'technical support', 'legal'],
#  'scores': [0.8185835480690002, 0.09302053600549698, 0.05521026626229286, 0.03318570926785469]}
```


일반적인 구현 중 하나는 자연어 추론(NLI)을 위해 학습된 모델을 사용합니다. 각 후보 레이블을 가설로 변환하고, 모델은 입력이 해당 가설을 얼마나 강하게 함의하는지 측정합니다.

이는 이미 의사결정 모델과 상당히 비슷하게 들립니다. 실제로 여러 측면에서 그렇습니다.

### 의사결정 모델이 다른 점

의사결정 모델은 입력을 단순히 카테고리에 할당하는 것을 넘어 이 아이디어를 확장합니다. 의사결정 모델은 동일한 상태에 대해 서로 다른 답변 유형을 가진 여러 개의 이름 있는 질문을 받을 수 있습니다. 유형에는 대안 중 하나를 선택하는 것(choice), 순서가 있는 척도에서 점수를 매기는 것(score), 명제가 참일 확률을 추정하는 것(noul)이 있습니다.

더 중요한 점은 인터페이스가 **가능한 결정에 대한 확률 분포**를 중심으로 설계되었다는 것입니다.

다음 세 가지 접근 방식을 생각해 보겠습니다.

| 속성 | 분류 | Zero-shot 분류 | 의사결정 모델 |
| --- | --- | --- | --- |
| 선택지에 대한 확률 | 예 | 예 | 예 |
| 추론 시 정의되는 레이블 | 아니요 | 예 | 예 |
| 유형이 지정된 여러 질문 | 아니요 | 아니요 | 예 |
| 순서가 있는 점수 및 yes/no 결정 | 작업별 | 조정으로 가능 | 기본 primitive |

의사결정 모델의 장점은 런타임에 정의되는 레이블이나 확률적 분류를 새롭게 발명했다는 데 있지 않습니다. 이러한 기능을 일관된 인터페이스로 구성하고, 특히 의사결정에 최적화된 아키텍처와 학습 절차를 기반으로 할 수 있다는 점에 있습니다.

## 의사결정 모델 인터페이스 {#section-4}

의사결정 모델 요청은 다음 두 가지 구성 요소로 이루어집니다.

1. state
2. questions

### State

state는 모델이 평가해야 하는 정보입니다. 문자열, 구조화된 JSON 객체 또는 지원되는 omni-modal 모델의 경우 다른 모달리티일 수 있습니다.

예를 들어:

```json
{
  "customer_message": "I was charged twice. Please refund me today.",
  "subscription": "pro",
  "previous_tickets": 2
}
```


### Questions와 해당 primitive

Questions는 상태에 대해 알고 싶은 내용을 설명합니다. 의사결정 모델 인터페이스에서는 세 가지 기본 primitive가 서로 다른 형태의 결정을 나타냅니다.

1. **Choice:** 여러 가능한 답변 중 하나를 선택합니다.
2. **Score:** 순서가 있는 척도에서 무언가를 평가합니다.
3. **Noul:** yes/no 질문에 확률적으로 답합니다.

하나씩 살펴보겠습니다.

#### Choice: 선택지에 대한 확률 분포

Choice는 가장 직관적인 primitive이며 전통적 분류에 가장 가깝습니다.

다음과 같이 질문한다고 가정해 보겠습니다.

> 이 고객 요청은 어느 부서에서 처리해야 하나요?

사용 가능한 선택지는 Billing, Technical support, Sales입니다.

```python
from transformers import pipeline

decide = pipeline("decision", model="autotrust/GEV-26B-Decide")
decision = decide(
    {
        "state": "I was charged twice for my order and want a refund.",
        "questions": {
            "department": {
                "type": "choice",
                "instructions": "Which team should handle this?",
                "criteria": {
                    "billing": "Payments and refunds",
                    "technical": "Bugs and technical issues",
                    "sales": "Pricing and subscriptions"
                }
            },
        }
    }
)

# {
#   'department': {
#     'type': 'choice',
#     'choice': 'billing',
#     'confidence': 0.9974000453948975,
#     'probabilities': {
#       'billing': 0.9982666969299316,
#       'technical': 0.0010246571619063616,
#       'sales': 0.0007087149424478412
#     }
#   }
# }
```


모델은 각 선택지에 로짓을 할당합니다. 로짓 ($z_1,\ldots,z_K$)이 주어졌을 때 (K개 클래스), softmax를 사용하여 확률을 얻을 수 있습니다.

$$
p_i=\frac{\exp(z_i/T)}{\sum_{j=1}^{K}\exp(z_j)}
$$

여기서 (K)는 선택지의 수입니다.

다음과 같은 예시 분포를 생각해 보겠습니다.

| 선택지 | 확률 |
| --- | --- |
| Billing | 0.998 |
| Technical support | 0.001 |
| Sales | 0.001 |

확률의 합은 1입니다.

$$
\sum_{i=1}^{K}p_i=1.
$$

모델은 확률이 가장 큰 선택지를 선택합니다.

$$
\hat y=\arg\max_i p_i
$$

이 경우 선택지는 Billing이며 확률은 0.998입니다. 하지만 나머지 확률도 유용합니다. 이 확률들은 모델이 대안들 사이에 자신의 믿음을 어떻게 분배하는지 알려 줍니다.

#### Score: 순서가 있는 분포의 기댓값

Choice는 서로 구분되는 여러 대안이 있을 때 작동합니다. 그렇다면 순서가 있는 척도에서 무언가를 측정하려면 어떻게 해야 할까요?

다음 질문을 생각해 보겠습니다.

> 이 고객 요청은 얼마나 긴급한가요?

세 가지 수준을 정의합니다.

* 0: 낮은 긴급도
* 1: 중간 긴급도
* 2: 높은 긴급도

```python
from transformers import pipeline

decide = pipeline("decision", model="autotrust/GEV-26B-Decide")
decision = decide(
    {
        "state": "I was charged twice for my order and want a refund.",
        "questions": {
            "urgency": {
                "type": "score",
                "instructions": "How urgent is the request?",
                "criteria": ["low", "medium", "high"]
            },
        }
    }
)

# {
#   'urgency': {
#     'type': 'score',
#     'score': 1.7053890228271484,
#     'legend': {
#       '0': 'low',
#       '1': 'medium',
#       '2': 'high'
#     },
#     'confidence': 0.5580834252759814,
#     'probabilities': {
#       '0': 0.014908230863511562,
#       '1': 0.26479458808898926,
#       '2': 0.7202972173690796
#     }
#   }
# }
```


모델은 다시 확률 분포를 생성합니다.

| 수준 | 확률 |
| :--: | :--: |
| 0 — 낮음 | 0.01 |
| 1 — 중간 | 0.26 |
| 2 — 높음 | 0.72 |

Score primitive는 가장 가능성이 높은 수준만 반환하는 대신 **수준 인덱스의 기댓값**을 계산합니다.

수준을 나타내는 확률 변수 (X)에 대해 기댓값은 다음과 같습니다.

$$
\mathbb{E}[X]=\sum_{i=0}^{K-1}ip_i
$$

이 예시에서는 다음과 같습니다.

$$
\mathbb{E}[X] = 0(0.01)+1(0.26)+2(0.72)=1.7
$$

따라서 보고되는 점수는 `1.7`입니다.

이는 모델이 중간과 높음 사이에 있는 가상의 수준을 선택했다는 뜻이 아닙니다. 모델의 확률 분포에 대한 기댓값이 1.7이라는 뜻입니다.

#### Noul: 베르누이 결정

세 번째 primitive는 이진 질문을 나타내는 Noul입니다.

예를 들어:

> 고객이 환불을 요청하고 있나요?

```python
from transformers import pipeline

decide = pipeline("decision", model="autotrust/GEV-26B-Decide")
decision = decide(
    {
        "state": "I was charged twice for my order and want a refund.",
        "questions": {
            "refund": {
                "type": "noul",
                "instructions": "Is the customer requesting a refund?"
            }
        }
    }
)

# {
#   'refund': {
#     'type': 'noul',
#     'noul': 0.9947046637535095
#   }
# }
```


선택지 목록을 정의하는 대신, 답변이 참일 확률을 반환하도록 모델에 요청합니다. 이는 베르누이 분포를 사용해 이해할 수 있습니다(noul은 Bernoulli에서 유래했습니다).

이진 결과를 나타내는 (Y)를 다음과 같이 정의합니다.

$$
Y\sim\operatorname{Bernoulli}(p)
$$

여기서

$$
P(Y=1)=p,\qquad P(Y=0)=1-p.
$$

모델이 다음을 반환한다고 가정해 보겠습니다.

```json
{"type": "noul", "noul": 0.92}
```


Yes에 `0.92`, No에 `0.08`의 확률을 할당합니다.

여기서 모델은 이진 답변을 무작위로 샘플링하지 않습니다. 확률 매개변수 자체를 반환하고, 애플리케이션이 이를 바탕으로 어떻게 동작할지 결정하도록 둡니다.

#### Confidence: 모델은 얼마나 확신하나요?

지금까지 모델에서 확률 분포를 얻었습니다. 하지만 의사결정 모델 인터페이스는 Choice와 Score에 대해 `confidence`라는 필드도 반환합니다.

전체 분포에는 여러 가능한 답변이 포함될 수 있으며, 모델의 믿음이 얼마나 집중되어 있는지를 요약하면 유용합니다. `confidence`를 사용하면 바로 이를 얻을 수 있습니다.

(K)개의 선택지가 있는 Choice에서 confidence는 다음과 같습니다.

$$
\frac{p_{\max}-\frac{1}{K}}{1-\frac{1}{K}}
$$

여기서 ($p_{\max}$)는 예측된 확률 중 가장 큰 값입니다.

여기서의 직관은 다음과 같습니다.

* 균등 분포의 confidence는 0입니다. ($p_{\max} = \frac{1}{K}$). 이는 모델이 모든 선택지가 동일한 확률을 가진다고 추정한다는 뜻입니다.
* 한 선택지에 완전히 집중된 분포의 confidence는 1입니다. ($p_{\max} = 1$)
* 균등 분포에 비해 우승 선택지의 확률이 클수록 confidence가 높습니다.

앞서 살펴본 세 선택지 예시에서 Billing의 확률은 0.80이었습니다.

$$
C=\frac{3(0.99)-1}{2}=0.98
$$

우승 확률은 0.99이지만 보고된 confidence는 0.98이라는 점에 주목하세요. confidence는 사용 가능한 선택지 수를 기준으로 가장 큰 확률을 정규화합니다. 반면 순서가 있는 Score 예시의 confidence는 0.558에 불과했습니다.

## Hugging Face 생태계의 의사결정 모델 {#section-5}

의사결정 모델은 새롭고 빠르게 변화하는 분야입니다. 각 모델은 내부적으로 서로 다른 방식으로 결정을 내립니다(전체 스키마를 함께 점수화하는 헤드, LLM 백본 위에 별도로 추가된 readout, 엣지 규모 및 멀티모달 변형 등). 이러한 다양성은 건전하지만 비용이 따릅니다. 모든 모델이 각자의 인터페이스를 노출하면 이를 둘러싼 모든 도구가 모델별 조정을 필요로 합니다.

Hugging Face의 목표는 공통 **구현**을 강제하지 않고 공통 **인터페이스**에 합의하는 것입니다. 의사결정 모델은 내부적으로 원하는 방식으로 자유롭게 작동하되, 동일한 state와 questions를 받아 동일한 유형의 결정을 반환해야 합니다. 이 계약이 존재하면 나머지 생태계는 이를 한 번만 기반으로 구축할 수 있습니다.

* llama.cpp와 같은 추론 엔진은 동일한 API를 통해 모든 의사결정 모델을 제공할 수 있습니다.
* Hub는 이를 일관된 방식으로 패키징하고 표시할 수 있습니다.
* 학습 도구는 개별 아키텍처가 아니라 공유 primitive를 대상으로 할 수 있습니다.

이 절의 나머지 부분에서는 이러한 각 요소를 차례로 살펴봅니다.

Hugging Face는 호환되는 모델을 찾을 수 있도록 전용 [`decision-model` 태그](https://huggingface.co/models?other=decision-model&sort=trending)를 도입했습니다. 의사결정 모델은 하나의 백본이나 아키텍처를 공유할 필요가 없기 때문에 유용합니다.

### 4. Hugging Face 도구를 사용한 의사결정 모델 학습

추론을 이해했다면 다음 질문은 의사결정 모델을 조정할 수 있는지 여부입니다. 의사결정 모델은 transformers에 통합되어 있으므로 `Trainer` API를 사용해 fine-tuning할 수 있습니다.

다음은 지원 요청을 라우팅하도록 `JEV-9B`을 fine-tuning하는 간단한 예시입니다. 의도적으로 작게 구성했지만, 중요한 부분을 보여 줍니다.

* 각 예시는 정답과 연결된 의사결정 요청(`state`와 `questions`)입니다.
* `model.decision_config.prepare_inputs`는 추론 시와 동일한 방식으로 요청을 모델 입력으로 변환합니다.
* 모델은 선택지마다 하나의 로짓을 반환하므로 `choice` 질문은 선택지에 대한 일반적인 cross-entropy loss로 학습합니다.

```python
import os; os.environ["CUDA_VISIBLE_DEVICES"]="2"
import torch
import torch.nn.functional as F
from transformers import AutoTokenizer, AutoModelForDecision, Trainer, TrainingArguments

checkpoint = "autotrust/JEV-9B"
tokenizer = AutoTokenizer.from_pretrained(checkpoint)
model = AutoModelForDecision.from_pretrained(checkpoint)

examples = [
    ("I was charged twice. Please refund me.", "refund"),
    ("My package has not arrived.", "shipping"),
    ("The application crashes when I open it.", "technical"),
    ("I want my money back.", "refund"),
    ("Where is my delivery?", "shipping"),
    ("I cannot log into my account.", "technical"),
]

options = {
    "refund": "Billing issues and refunds",
    "shipping": "Orders and deliveries",
    "technical": "Software and account issues",
}

def preprocess(text, label):
    request = {
        "state": text,
        "questions": {
            "category": {
                "type": "choice",
                "instructions": "Classify the support request.",
                "criteria": options,
            }
        },
    }
    (inputs, questions), = model.decision_config.prepare_inputs(
        request, tokenizer
    )
    inputs["marks"] = inputs["marks"].unsqueeze(0)
    inputs["num_options"] = torch.tensor([[len(questions[0].options)]])
    inputs["question_type_ids"] = torch.tensor([[1]])  # choice
    inputs["labels"] = torch.tensor(
        [questions[0].options.index(label)]
    )
    return inputs

dataset = [preprocess(text, label) for text, label in examples]


class DecisionTrainer(Trainer):
    def compute_loss(self, model, inputs, return_outputs=False, **kwargs):
        inputs = inputs.copy()
        labels = inputs.pop("labels")
        logits = model(**inputs)

        logits = logits.unsqueeze(0)  # [3] -> [1, 3]
        loss = F.cross_entropy(logits.float(), labels)

        return (loss, logits) if return_outputs else loss


trainer = DecisionTrainer(
    model=model,
    args=TrainingArguments(
        output_dir="./decision-toy",
        max_steps=30,
        per_device_train_batch_size=1,
        learning_rate=1e-3,
        logging_steps=5,
        save_strategy="no",
        report_to="none",
        remove_unused_columns=False,
    ),
    train_dataset=dataset,
    data_collator=lambda batch: batch[0],
)

trainer.train()
```


의사결정 모델 학습에 대한 일급 지원도 TRL에 추가될 예정이므로([huggingface/trl#8040](https://github.com/huggingface/trl/pull/8040)), 이러한 연결 코드를 직접 작성할 필요가 없어집니다. 이 글을 작성하는 시점에는 PR이 아직 열려 있습니다.

더 나아가 생성형 LLM을 의사결정 모델로 전환하려는 경우, [Unsloth가 레시피를 제공합니다](https://unsloth.ai/docs/basics/train-your-own-decision-model-with-unsloth). 이 레시피는 Qwen과 같은 모델을 LoRA 및 의사결정 점수화 헤드와 함께 fine-tuning합니다.

## 마무리 {#section-6}

의사결정 모델이 흥미로운 이유는 분류가 새롭기 때문이 아니라, **소프트웨어를 위한 결정과 확률을 일급 출력으로 만든다는 점**에 있습니다.

기존 분류기는 이미 확률을 생성하며, zero-shot 분류기는 런타임에 정의되는 카테고리를 이미 허용합니다. 의사결정 모델은 이러한 아이디어를 여러 질문 primitive, 비생성 점수화, 신뢰할 수 있고 보정된 결정을 위한 특화 학습의 가능성을 갖춘 유형 지정 인터페이스로 통합합니다.
